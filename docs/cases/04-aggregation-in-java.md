# Кейс 04. Агрегация в Java вместо SQL

**Эндпоинт:** `GET /api/customers/{id}/stats`
**Код:** `CustomerService.getStats`
**Тест:** `Case04AggregationInJavaTest`

## Ситуация

Личный кабинет показывает статистику клиента: количество заказов, разбивку по статусам, сумму покупок,
средний чек и любимую категорию. Код читается красиво — стримы, коллекторы. Но чтобы посчитать
пять чисел, приложение загружает все заказы клиента, все позиции, все товары и их категории.

У нашего клиента ~10–15 заказов. А у оптового клиента их может быть 50 000.

## Как воспроизвести

```bash
curl "http://localhost:8080/api/customers/1/stats"
```

Найдите клиента с максимальным количеством заказов (SQL!) и сравните время и число запросов.

## Задание

1. Перенесите вычисления в БД. Сущности `Order`/`OrderItem` для статистики загружаться не должны вовсе.
2. Подумайте, сколько запросов нужно: один большой или несколько простых? Аргументируйте.
3. Результат возвращайте через проекции (DTO/record/interface), а не через сущности.
4. Учтите граничные случаи: клиент без заказов, клиент только с отменёнными заказами.

**Готово, когда:** `Case04AggregationInJavaTest` зелёный (0 загруженных `Order`/`OrderItem`, ≤ 3 запроса, результат совпадает с эталоном).

## Подсказки

<details><summary>Подсказка 1</summary>

`count(...)`, `sum(...)`, `group by` есть и в JPQL. Агрегат с условием в PostgreSQL удобно писать через `filter (where ...)`
или `sum(case when ... then ... end)`.
</details>

<details><summary>Подсказка 2</summary>

«Любимая категория» — это `group by` + `order by` + `limit 1`. Порядок при равенстве количества
должен совпадать с текущей реализацией (по имени категории по возрастанию).
</details>
